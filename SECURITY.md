# Security policy — GoreeCloud Database

**Development preview. Do not deploy on an Internet-facing host.** No production SLA, audit or vulnerability-response guarantee is established.

- Report suspected vulnerabilities privately using GitHub's private vulnerability-reporting feature if enabled, rather than publishing exploit steps or secrets.
- Generated `.env` must remain local and uncommitted. `scripts/init_env.py` never prints secrets and refuses to overwrite them.
- Database, API and REST services are isolated on a private data network; only the nginx gateway is published on localhost. The unauthenticated `/api/readyz` endpoint checks private SELECT-only database connectivity and exposes status only; never expose the development gateway on public ingress. REST is available via /rest/ on that gateway. External access requires a separately evaluated, identity-aware TLS proxy.
- Backend authorization uses independent shared admin/viewer bearer tokens. [OIDC RS256 verification](docs/OIDC_READER.md) still grants **global reader only** for existing catalog and object APIs, after strict issuer/audience/scope/signature/expiry checks. Only an additional explicit `goreecloud.database.write` claim permits [owner-isolated personal notes INSERT](docs/PERSONAL_RLS.md) under PostgreSQL RLS, never administrator writes or platform-wide tenant isolation. Reads use a separate SELECT-only role. Rotate shared and OIDC credentials using their respective approved processes.
- Use a non-superuser `gc_api` for the management API. SQL identifiers are allowlisted and quoted; values are parameterized.
- Android refuses plaintext HTTP and does not persist administrator tokens. [Native and web private-notes clients](docs/PERSONAL_CLIENTS.md) require manually supplied signed OIDC tokens and ephemeral screen state, not PKCE login or certified offline privacy controls.
- Bounded CSV page export reads through `gc_reader`, escapes spreadsheet formula prefixes and uses 2 MiB limits. This is **not** a per-user privacy export; global viewer credentials read the exposed `app` tables.
- [Confirmed private-note deletion](docs/PERSONAL_ERASURE.md) requires a signed, explicitly scoped OIDC token, exact confirmation and PostgreSQL FORCE RLS on the signed subject. It removes the live-table row, **not** WAL/backups or retained copies, and is not independently certified GoreeShield erasure.
- [Single-object deletion](docs/OBJECT_DELETION.md) is shared-administrator-only, requires explicit confirmation and a matching SHA-256, and removes one UUID under non-superuser `gc_api` privileges. The audit trigger records operation-only metadata; backups and WAL may retain copies. This is **not** guaranteed personal-data erasure.
- An optional [SeaweedFS S3 sandbox](docs/S3_PREVIEW.md) has separately generated high-entropy credentials, loopback-only S3 ingress, **dedicated networks isolated from the PostgreSQL/API network**, and the WebDAV/Admin services disabled. The S3 integration test must prove anonymous listing denial before acceptance. It is not connected to the PostgreSQL object API or per-user OIDC/RLS policies; do not put personal data into it or expose it publicly.
- The opt-in [pure Wasmtime edge lab](docs/EDGE_PREVIEW.md) runs only SHA-approved, no-import WebAssembly on a development CLI with bounded fuel/stack and no WASI. It is **not** a production OS-isolated untrusted-code sandbox, remotely exposed functions API or artifact-signing system.
- This service does not yet offer certified disaster recovery, **platform-wide** tenant RLS, actor-attributed/tamper-evident auditing, distributed identity-scoped rate limiting, or multi-factor identity. The isolated [personal notes RLS example](docs/PERSONAL_RLS.md) is not a tenant boundary for general `app`/`gc_storage` schemas; shared viewer tokens still read those exposed records. A [minimal change metadata trail](docs/AUDIT_METADATA.md) records operations without row values or subjects; it lacks retention/tamper evidence. Shared-admin writes have only a [30/minute per-process throttle](docs/WRITE_THROTTLE.md). Catalog SSE is lossy and not tenant-scoped. Object storage remains limited to 1 MiB per file / 512 files / 128 MiB globally, without per-user object ACL, virus scanning, owner-scoped quotas or retention controls.
